LiteOffice｜去掉文件大小限制（0 截断）—— 修复任务书

版本 v1.1   日期 2026-10-24
对象：liteoffice-vue 工程（code/frontend）
目标：任何文件都不再被静默截断，且不会因为"取消限制"而卡死或白屏。
原则：只改"装载与渲染策略"，解析算法、主题、布局、导出逻辑一律不许动。


================================================================
【一、先说结论：不是"删掉限制"就完事】
================================================================

如果只是删掉 MAX_FILE_BYTES，页面一定会崩。原因是三个物理边界：

  边界              数字                        不加处理会怎样
  ────────────────────────────────────────────────────────────────
  DOM 节点数        10 万节点之后明显变慢，        5 万行 × 20 列 = 100 万
                    100 万节点基本不可用          单元格一次性渲染 → 页面卡死

  内存              单标签页约 2–4 GB 上限；       20 MB docx 可能占 200–400 MB；
                    DOM 通常比原始文件大 5–20 倍    100 MB 以上 → 标签页崩溃（Aw, Snap）

  主线程            单任务超过 200ms 就"卡"        实测解析 6.7 MB xlsx 需 5.5 秒，
                                                  在主线程会让整页冻结，连"取消"都点不动

所以"不限制文件大小"能成立的前提是三条同时做到：

  ① 分批渲染：一次只往 DOM 里放有限节点
  ② 虚拟滚动：只渲染可视区，滚走的从 DOM 移除
  ③ Web Worker：解析不占主线程，界面始终能响应与取消

缺任何一条都会卡死。因此本任务书要求的是
「删限制 + 换渲染方式」，而不是单纯删掉常量。

实测（headless Edge + 真实文件）

  md > 4 MB        → 只读前 4 MB，后半段完全不显示，仅顶部一行小字

                     界面显示"已截断，仅显示前 20000 行（共 50000 行）"
  docx / pdf / pptx → 全量解析，没有 4 MB 限制

用户反馈原话：截断不太好，要"不限制文件大小"。


================================================================
【三、目标与实施顺序】
================================================================

硬目标

  · 任何格式都不再有"只处理前 N 字节 / 前 N 行 / 前 N 段"
  · 打开的文件内容必须 100% 可访问（能找到最后一个字、最后一行、最后一页）
  · 大文件打开过程中界面可响应、可取消、有进度
  · 内存真的不够时给出明确原因与替代方案，不白屏

实施顺序（必须按此顺序，不许颠倒）

  第 1 步  实现分批渲染 + 虚拟滚动（md 块级、表格行级、PDF 页级）
  第 2 步  把 docx / xlsx / md 解析移入 Web Worker
  第 3 步  加内存监控与分级提示（见 §五）
  第 4 步  最后才删除 MAX_FILE_BYTES 与 FALLBACK_MAX_ROWS 等常量

  理由：先删常量再做虚拟化，中间任何一个版本都会卡死，无法验收。


================================================================
【四、必须做的六件事】
================================================================

1. 删除全部截断逻辑
   · 删掉 MAX_FILE_BYTES 与 decodeText 里的 subarray
   · 删掉 workspace.ts 里所有 buffer.slice(0, MAX_FILE_BYTES)
   · 删掉"已截断"相关文案与 notices
   · 删掉界面上的"单文件 ≤ 4 MB"

2. 删除装载上限
   · FALLBACK_MAX_ROWS / FALLBACK_MAX_CELLS 不再作为硬上限
   · gateLargeWorkbook 的"只读前 20000 行"分支删除
   · 保留确认提示，但按钮文案必须是"继续打开全部"

3. 分批渲染 + 虚拟滚动
   · Markdown：先渲染前 500 块；滚动接近底部再追加 500 块，直到文末
   · 表格：按行区间懒加载（每批 2000 行）；滚动到边界再解析下一批；
     只保留可视区 ±200 行的 DOM 节点
   · PDF：只渲染可视页 ±2 页，其余显示占位；翻页时再渲染
   · docx 大图：进入可视区前用占位尺寸，滚动到位再解码

4. 解析移入 Web Worker
   · docx / xlsx / md 的解析都在 Worker 内完成
   · 主线程只负责渲染与进度
   · 进度必须可见：已处理字节 / 段落数 / 行数
   · 必须能取消：取消后不残留半个文档，不留下内存垃圾

5. 分级提示（只提示，不阻止）
   · < 16 MB        静默打开，不提示
   · 16–64 MB       顶部提示"文件较大（N MB），打开可能需要数十秒，可随时取消"
                    → 用户可继续，也可取消
   · > 64 MB        提示"文件较大（N MB），可能超出浏览器内存；
                    建议下载后用桌面软件打开"
                    → 仍提供"继续尝试打开"与"下载原始文件"两个按钮
   · 打开过程中显示"已加载 X / 共 Y"（段落或行或页）

6. OOM / 异常兜底
   · 捕获 RangeError、Worker 崩溃、ArrayBuffer 分配失败
   · 提示："文件 X MB，超出本机浏览器可用内存，已停止解析。
           本地功能未受影响，可下载原文件用桌面软件打开。"
   · 必须提供"下载原始文件"按钮
   · 不允许白屏、不允许无限转圈、不允许静默丢弃内容


================================================================
【五、必须删除 / 可以保留的文案】
================================================================

必须删除
  "单文件 ≤ 4 MB"
  "已截断"
  "只读前 20000 行"
  "文件超过 4 MB，已截断至 4 MB 以内处理"
  "文件超过 4 MB，已截断并仅保留前 4 MB 内容"

可以保留（仅提示）
  "文件较大（87 MB），打开可能需要 30 秒以上，期间可以取消。"
  "已加载全部内容：第 50000 行 / 共 50000 行"
  "文件 120 MB，可能超出浏览器内存，建议下载后用桌面软件打开。"


================================================================
【六、禁止事项】
================================================================

  · 不接受任何 silent truncation（含"为了性能只读前 N 段"这类说法）
  · 不接受用"文件过大，请用桌面版"直接拒绝打开
  · 不引入新第三方依赖（不装虚拟列表库、不装 react-window 类库，自己写）
  · 不改 docx / pdf / md 的解析算法本身（只改装载与渲染策略）
  · 不改主题、布局、路由、导出逻辑
  · 不允许把"先删限制、以后再做虚拟化"当成两期交付

【七、验收：必须自己跑，把数字贴出来】
================================================================

A. Node 侧自检脚本 scripts/check-large-file.mjs（不参与构建）

   用法：node scripts/check-large-file.mjs

   它自己生成测试文件并断言：

   1) 8 MB 的 md
        12 万个段落，末尾追加唯一标记 END-OF-FILE-MARK-9F3A
        断言：块数 ≥ 120000
              渲染结果包含 END-OF-FILE-MARK-9F3A     ← 不能丢末尾

   2) 5 万行 × 20 列 xlsx（约 100 万单元格）
        末行第一列写 LAST-ROW-MARK-7C1B
        断言：行数 = 50000
              最后一个单元格 = LAST-ROW-MARK-7C1B    ← 不能截断
              输出中不出现"截断"字样

   3) 500 页 PDF
        末页写 LAST-PAGE-MARK-2D8E
        断言：页数 = 500，文本包含 LAST-PAGE-MARK-2D8E

   4) 20 MB docx（50 张图 + 2000 段）
        断言：图片数 = 50，段落数 ≥ 2000

   5) 每项打印：耗时(ms) / 峰值内存(MB) / 通过与否
      任一项不通过 → 退出码 1

B. 浏览器侧验收（headless 或手动均可，必须实测）

   a) 8 MB md
        能打开，滚动到底部能看到 END-OF-FILE-MARK-9F3A
        首屏可交互 < 2 秒；滚动时无长时间白屏

   b) 5 万行 xlsx
        能滚动到第 50000 行并看到 LAST-ROW-MARK-7C1B
        界面显示"已加载第 50000 行 / 共 50000 行"
        界面上不出现"已截断"

   c) 500 页 PDF
        能翻到第 500 页并看到 LAST-PAGE-MARK-2D8E

   d) 20 MB docx
        图片能显示，末尾段落能看到

   e) 全程 Network 面板：无任何第三方域名请求（保持"不上传"）

C. 卡死与崩溃的验收

   f) 打开 8 MB md 期间，点击"取消"应在 1 秒内生效，
      界面恢复可用，不留下半个文档

   g) 构造一个必然超内存的场景（如 200 MB md），
      应出现"超出可用内存"的明确提示 + "下载原始文件"按钮，
      不得白屏、不得无限转圈

D. 交付说明里必须回答

   · 删掉了哪几处截断（文件 + 行号）
   · 分批大小：md 每批多少块、表格每批多少行、可视区保留多少行
   · Worker：有几个、总体积多大、进度如何上报
   · 8 MB md 的首屏时间、滚到末尾的耗时
   · 5 万行 xlsx 的打开总耗时
   · 200 MB 场景的实际表现（截图或日志）
   · npm run build 是否通过、vue-tsc 是否零错误
   · dist 体积变化（当前：主包 208 KB / pdf.worker 1.38 MB / pdf 329 KB / sheetjs 424 KB）
