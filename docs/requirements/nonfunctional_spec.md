# 非功能需求规范（Non-Functional Specification）

> 文档编号：REQ-NFS-001  
> 版本：1.0  状态：已评审  
> 关联：`problem_definition.md`、`functional_spec.md`

每条非功能需求都给出**可测量的指标**和**测量方法**，并标注**当前实测值**。
没有测量方法的需求不写进来——无法验收的需求等于没有需求。

---

## 1. 性能（PERF）

### NFR-PERF-01 预览首屏时间

| 项 | 内容 |
|---|---|
| 需求 | 打开 docx / xlsx / pptx / pdf 后，内容在 **1 s 内**可见 |
| 测量方法 | Chrome Performance 面板，从「拖放 drop 事件」到「首次内容绘制」 |
| 当前实测 | docx 预览组件 1.2 MB，本地加载 **< 1 s**；xlsx 13.5 MB 约 1–2 s |
| 优先级 | P0 |

### NFR-PERF-02 编辑模式首次加载时间

| 项 | 内容 |
|---|---|
| 需求 | 局域网首访 **≤ 180 s**；本机已缓存时 **≤ 10 s** |
| 测量方法 | 编辑器加载遮罩显示的「已等待 N 秒」即为该指标的直接读数 |
| 当前实测 | 本机缓存后约 5–10 s；局域网未缓存需 1–3 min |
| 说明 | 制约因素是 199 MB 静态资源，其中 `x2t.wasm` 单文件 56 MB |
| 优先级 | P0 |

### NFR-PERF-03 预览资源按需加载

| 项 | 内容 |
|---|---|
| 需求 | 只打开 docx 时，**不得**下载 excel / pptx / pdf 的预览包 |
| 测量方法 | Chrome Network 面板过滤 JS，检查是否出现 `@vue-office/excel` 相关 chunk |
| 当前实测 | 通过 `src/lib/preview.ts` 的动态 `import()` 实现，实测只加载对应格式 |
| 优先级 | P1 |

### NFR-PERF-04 交互响应

| 项 | 内容 |
|---|---|
| 需求 | 侧栏切换文档、模式切换的界面响应 **≤ 100 ms**（不含渲染内核加载） |
| 测量方法 | 点击后观察状态栏/高亮变化是否即时 |
| 当前实测 | 状态切换即时；内容渲染依赖对应内核 |
| 优先级 | P1 |

## 2. 资源占用（RES）

### NFR-RES-01 源码体积

| 项 | 内容 |
|---|---|
| 需求 | 入库源码 **≤ 1 MB**（不含依赖与生成资源） |
| 测量方法 | `git ls-files | xargs du -ch` 或统计仓库中排除 `node_modules`/`public/onlyoffice`/`dist` 的文件 |
| 当前实测 | **36 个文件 / 162 KB** |
| 优先级 | P1 |

### NFR-RES-02 运行时静态资源

| 项 | 内容 |
|---|---|
| 需求 | 预览路径的增量资源 ≤ 20 MB／格式；编辑路径整体 ≤ 250 MB |
| 测量方法 | `dist/` 或 `public/onlyoffice` 目录体积 |
| 当前实测 | `public/onlyoffice` = **356 文件 / 198.5 MB**；预览包 docx 1.2 / xlsx 13.5 / pptx 9.3 / pdf 16.4 MB |
| 优先级 | P1 |

### NFR-RES-03 浏览器内存

| 项 | 内容 |
|---|---|
| 需求 | 打开一个 10 页 docx 并进入编辑后，标签页内存 **≤ 1.5 GB** |
| 测量方法 | Chrome 任务管理器查看该标签页「内存占用」 |
| 当前实测 | 未系统测量；实测进入编辑后可正常操作，未出现崩溃 |
| 优先级 | P2 |
| 备注 | 56 MB 的 WASM 实例化会占用较大内存，低配机器上可能失败（见 NFR-COMPAT-02） |

### NFR-RES-04 资源释放

| 项 | 内容 |
|---|---|
| 需求 | 切换 / 关闭文档后，旧的编辑器实例、`blob:` URL、事件监听必须释放 |
| 测量方法 | 连续切换 5 个文档后，在 DevTools Memory 中检查 `blob:` URL 数量不持续增长 |
| 实现 | `editorAdapter.ts` 的 `dispose()`：`unmount()` + `revokeObjectURL()` + `removeEventListener` |
| 优先级 | P1 |

## 4. 技术选型实测（依据本规范的关键指标）

这一节是本项目的核心工程论证：**为什么不自研引擎，为什么同时用两个渲染库**。

### 4.1 两条路线对比（均为实测数据）

| 指标 | 自研零依赖内核（同期实践） | 本项目（复用 ONLYOFFICE） |
|---|---|---|
| 源码规模 | 99 个 `.ts`／29,893 行 | 19 个源文件／约 1,500 行 |
| 自动化测试 | 369 个（368 通过／0 失败／1 跳过） | 0（依赖手动验收，见第 7 节） |
| 运行时依赖 | **0 个** | 6 个（约 400 MB） |
| 格式覆盖 | 29 种可打开 | 4 种（docx/xlsx/pptx/pdf） |
| **能否编辑** | **不能** | **能** |
| 打开耗时 | 20 ms 量级 | 预览 < 1 s；编辑首次 1–3 min |
| 风险 | 已完工 | 集成复杂、保存链路脆弱 |

**结论：自研内核在"轻量"和"格式覆盖"上碾压，但不满足"可编辑"这一核心目标；
因此主线选择成熟内核，自研成果作为技术对比与预览能力的备选论据。**

### 4.2 为什么预览和编辑用两个库

| | 预览（`@vue-office/*`） | 编辑（`onlyoffice-web-local`） |
|---|---|---|
| 渲染方式 | 解析为 DOM | WASM + Canvas |
| 体积 | 1.2–16.4 MB（按需） | 199 MB |
| 只读/可写 | 只读 | 可写 |
| 适用场景 | 看一眼、核对内容 | 真正修改 |

若统一用编辑器，则"只想看一眼"也要付 199 MB 代价——这与"轻量"定位直接冲突。
**按场景分模式是本项目最重要的架构决策之一。**

### 4.3 为什么编辑区用 iframe 隔离（实测驱动）

| 挂载方式 | 结果 |
|---|---|
| 直接挂载到三栏布局中的子区域 | 文档能显示，但**光标固定在文字上方约一行** |
| 官方 demo（整页环境） | 光标正常 |
| **独立页面 + iframe 隔离（采用）** | 光标正常 |

原因：该库按整页应用设计（容器 `height:100vh`、路由带 `?url=`），
在子区域内其坐标系与显示区域不一致。

## 5. 兼容性（COMPAT）

### NFR-COMPAT-01 浏览器支持

| 项 | 内容 |
|---|---|
| 需求 | 在 Chrome / Edge **近两年版本**上核心功能可用 |
| 硬性前提 | 支持 WebAssembly 与 ES Modules |
| 明确不支持 | 360 / QQ / 搜狗等旧内核浏览器可能无法加载编辑内核（须提示，见 NFR-USAB-03） |
| 优先级 | P0 |

### NFR-COMPAT-02 运行环境下限

| 项 | 内容 |
|---|---|
| 需求 | 编辑模式在内存 ≥ 8 GB 的设备上应可用 |
| 风险 | 56 MB WASM 实例化对内存敏感；低配设备可能失败 |
| 处理 | 超时/失败时提示"可能内存不足，可先用预览模式" |
| 优先级 | P1 |

### NFR-COMPAT-03 移动端 / 局域网

| 项 | 内容 |
|---|---|
| 需求 | 同一局域网内另一台设备可打开页面并完成预览 |
| 测量方法 | 手机连同一 WiFi 访问 `http://<内网IP>:<端口>/` |
| 当前实测 | 页面可打开、预览可用；编辑需满足 NFR-PERF-02 的等待时间 |
| 优先级 | P1 |

## 6. 可用性（USAB）

### NFR-USAB-01 失败必须可读

| 项 | 内容 |
|---|---|
| 需求 | 任何失败都不得以「白屏」「无反应」呈现；必须给出可读原因 |
| 实现 | `src/lib/errors.ts` 全局错误横幅 + `EditorHost.vue` 加载遮罩 |
| 验收 | 人为触发装载失败后，页面框架保留、横幅可见、可切换到预览继续用 |
| 优先级 | **P0** |

### NFR-USAB-02 长耗时操作可见

| 项 | 内容 |
|---|---|
| 需求 | 超过 1 s 的操作必须有进度反馈 |
| 实现 | 编辑器加载遮罩显示「已等待 N 秒」，>60 s 追加提示 |
| 优先级 | P1 |

### NFR-USAB-03 文案具体

| 项 | 内容 |
|---|---|
| 需求 | 提示文案必须说明**发生了什么**和**下一步怎么做**，禁止"操作失败"这类空话 |
| 反例 | ❌「保存失败」 ✅「没找到编辑器里的导出按钮，请直接在工具栏点导出后再点这里的保存」 |
| 优先级 | P1 |

## 7. 可维护性（MAINT）

### NFR-MAINT-01 类型安全

| 项 | 内容 |
|---|---|
| 需求 | `npm run typecheck`（`vue-tsc --noEmit`）**零错误**，且不得用 `any` 绕过 |
| 说明 | `vue-tsc` 会真正编译 `.vue` 模板，可抓到模板语法错误 |
| 当前实测 | 零错误 |
| 优先级 | P0 |

### NFR-MAINT-02 编码完整性

| 项 | 内容 |
|---|---|
| 需求 | 仓库内文本文件不得含 BOM、不得出现中文乱码 |
| 实现 | `npm run check:enc`（`scripts/check-encoding.mjs`） |
| 背景 | 本项目开发期间**真实发生三次**编码事故，均由 shell 文本往返造成 |
| 当前实测 | 29 个文件检查通过 |
| 优先级 | P0 |

### NFR-MAINT-03 编辑器可替换

| 项 | 内容 |
|---|---|
| 需求 | 更换渲染/编辑内核时，改动范围限 `src/lib/editorAdapter.ts` 与 `src/editor/` |
| 验收 | `grep -ri "onlyoffice" src/components src/App.vue` 无结果 |
| 优先级 | P1 |

### NFR-MAINT-04 注释解释"为什么"

| 项 | 内容 |
|---|---|
| 需求 | 关键取舍必须写清原因与反例，避免后来者重复踩坑 |
| 示例 | 「为什么用 iframe」「为什么保存要挂钩 `createObjectURL`」「为什么 `prepare-vue-office.mjs` 必须存在」 |
| 优先级 | P1 |

### NFR-MAINT-05 可复现的首次运行

| 项 | 内容 |
|---|---|
| 需求 | 全新克隆后，`npm install && npm run setup && npm run dev` 即可运行，无需人工干预 |
| 风险点 | npm 11 默认跳过 postinstall，导致 `@vue-office` 入口缺失 |
| 实现 | `scripts/prepare-vue-office.mjs` 幂等补齐 |
| 优先级 | P0 |

### NFR-LEGAL-02 商业字体（**当前未满足**）

| 项 | 内容 |
|---|---|
| 需求 | 不打包商业字体；如需中文排版，使用开源替代字体并配置 `fontSubstitutes` |
| 现状 | ❌ **未满足** |
| 实测依据 | 解析 `public/onlyoffice/fonts/` 中 16 个文件的 TTF `name` 表，确认包含：<br>`DengXian`（等线 / 等线 Light）、`SimSun`（宋体）、`Arial`、`Courier New`、`MS UI Gothic`、`Segoe UI Symbol`、`Symbol`、`Wingdings` |
| 影响 | 课程作业的内网/本机使用风险较低；**公开分发、商用、对外服务前必须替换** |
| 处理方案 | ① 换为思源黑体 / Noto Sans SC / Liberation / Carlito / Caladea；② 更新字体清单与映射；③ 回归中文排版与光标位置 |
| 优先级 | **P0（若公开分发）** |
