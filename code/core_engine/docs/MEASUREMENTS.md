# 实测数据与方法学

本文记录 LiteOffice 的**实测**内存与性能数字，以及这些数字是怎么测出来的。
「省内存」是本项目的核心主张，因此这里既给结论，也给**读这些数字时必须知道的限制**。

复现方式：

```powershell
cd C:\deepseekharness\liteoffice
node --expose-gc bench/bench.mjs            # 含合成夹具
node --expose-gc bench/bench.mjs --no-synthetic   # 只测本机真实文件
node tools/validate.mjs                     # 真实文件回归：成功率 + 降级清单
```

完整结果写到 `bench/out/BENCHMARKS.md` 与 `bench/out/VALIDATION.md`（均自动生成）。

---

## 一、测量方法

| 项 | 做法 |
|---|---|
| 堆增量 | 解析前 `forceGc()` 取基线，解析后取堆用量之差 |
| 峰值 | 5 ms 轮询采样，因此是**下界**而非真实峰值 |
| 模型体积 | UDM 结构的深估算（字符串按 2 字节/字符保守估）；表格体积由 `Grid.estimateBytes()` 自报 |
| 泄漏检查 | 同一文档反复打开 + `dispose()` 15 次，对残留量做线性回归，取斜率（B/次） |
| GC 可控性 | 未加 `--expose-gc` 时输出会明确标注「数字偏噪声」 |

### 三个必须知道的限制

**① 堆增量**不包含源文件缓冲。**文件是在取基线之前读进内存的**，
所以对「零拷贝」实现（把图片字节以 `subarray` 视图挂在源缓冲上）而言，
真实占用应再加上源文件大小。看绝对数字时请把这一点算进去。

**② 模型体积是估算，不是 V8 的真实占用。** 它用于比较不同格式/不同实现的相对开销，
以及观察「模型 ÷ 源文件」是否随功能增加而恶化 —— 不适合当作精确的内存预算依据。

**③ 我们不在基准里伪造 WPS 的实测数字。** 本机没有可复现的 WPS 测量环境，
因此与 WPS 的对比只以**设计差异**的形式陈述（见 [WHY-LIGHT.md](WHY-LIGHT.md)），
不给假的对照数据。

## 二、实测结果

数据来自 2025 年本机一次完整运行（Node v24，`--expose-gc`，Windows x64）。
**数字会随文件与机器变化，请以自己跑的 `bench/out/BENCHMARKS.md` 为准。**

### 真实 Word 文件（Word 生成，含图片与表格）

| 文件 | 源 | 模型估算 | 模型/源 | 堆增量 | 耗时 |
|---|---:|---:|---:|---:|---:|
| 二极管伏安特性实验报告.docx | 753 KiB | 967 KiB | 128% | 6.0 MiB | 117 ms |
| 实验报告-1N4001伏安特性.docx | 451 KiB | 562 KiB | 125% | 8.0 MiB | 55 ms |
| testA_nogrid.docx（含 18 张图） | 714 KiB | 858 KiB | 120% | 4.7 MiB | 55 ms |

要点：模型体积约为源文件的 1.2 倍（把压缩的 XML 展开成对象是有代价的，属于正常范围），
解析 700 KiB 的文件在 50–120 ms 量级。

### 真实 Excel 工作簿（WPS/Excel 生成）

| 文件 | 源 | 模型估算 | 耗时 |
|---|---:|---:|---:|
| 2025年秋季学期第十三周主题班会汇总表.xlsx | 12.3 KiB | 55.7 KiB | 28 ms |
| 第十期入党积极分子培训考试成绩.xlsx | 12.1 KiB | 48.1 KiB | 14 ms |

### 合成大表：低内存主张的主要证据

由 `bench/fixtures.ts` **按 ECMA-376 规范独立生成**（与读取器无共享代码），可复现。

| 文件 | 源 | 模型估算 | 模型/源 | 堆增量 | 耗时 |
|---|---:|---:|---:|---:|---:|
| 大型工作簿.xlsx（50,000 行 × 20 列 = 100 万单元格） | 6.6 MiB | **1.9 KiB** | 0.0% | 8.8 MiB | 404 ms |
| 大表格.csv（20,000 行 × 8 列） | 1.9 MiB | 3.7 MiB | 197% | 60.4 MiB | 111 ms |
| 大文本.txt | 4.0 MiB | 12.1 MiB | 306% | 23.9 MiB | 329 ms |
| 长文档.md | 306 KiB | 9.2 MiB | 3087% | 18.2 MiB | 324 ms |

**100 万单元格的工作簿，模型只有 1.9 KiB** —— 这是惰性网格的直接结果：
表体从未被物化，`Sheet` 只持有「怎么再读一次」的方法与一个小 LRU 缓存。
`readRows(任意窗口)` 都能取到正确数据（见 `test/cross-validation.test.ts`）。

对照：同样规模的 CSV（20,000 × 8 = 16 万单元格）走的是**物化**路径，模型 3.7 MiB ——
两者差 2000 倍，正好量化了「惰性 vs 物化」的差距。

### 真实 PowerPoint（图片型，11.3 MiB 中 11.5 MiB 为图片）

| 文件 | 源 | 模型 | 堆增量 | 耗时 |
|---|---:|---:|---:|---:|
| 我的暑假游玩经历.pptx | 11,586 KiB | 12 KiB | 3,213 KiB | 25 ms |
| 22.1一元二次方程(1).pptx（22 页，123 形状） | 472 KiB | 387 KiB | 3.9 MiB | 165 ms |

注意：该文件的图片字节**并未驻留内存**（`imageBytes` 报的是文档中图片的总大小，
而非已加载字节）。这个字段的语义目前在 docx 与 pptx 之间不一致，属于**已知的待澄清项**。

### 泄漏检查（最重要的健康指标）

```
文件：我的暑假游玩经历.pptx    次数：15 次打开 + dispose
残留  首次 -188.5 KiB / 末次 -74.8 KiB / 最大 -74.8 KiB
斜率  10,240 B/次   ->  ✅ 未检出累积泄漏
```

这一条验证的是**「关闭文档后内存真的会回落」** —— 办公软件长期使用后内存持续上涨，
正是这个环节没做好。判据是线性回归斜率 > 64 KiB/次 视为可疑；
实测 10 KB/次，且**残留全为负值** —— 表示每次测量期间 GC 回收的比分配的多，
这是「没有累积」比「残留为零」更强的证据。

> 残留为负**不是**测量失败：早期 `formatBytes()` 把负值显示成 `n/a`，
> 让报告看起来像「测不出来」。现在负值带符号显示，只有 NaN/Infinity 才是 `n/a`。

## 三、真实文件回归（`tools/validate.mjs`）

扫描本机 `Desktop / Documents / Downloads / OneDrive`（深度 ≤ 2）：

```
尝试 139 个（跳过 1 个）
打开成功 122   真失败 0   成功率 100.0%
按设计的拒绝 17 个（旧版二进制 16 + 加密 1），不计入成功率分母；声称支持 122 个
有降级告警 57 个（打开了但丢了内容，见下方清单）
源文件合计 88.6 MiB  ->  模型合计 17.6 MiB
平均解析耗时 约 20 ms
```

（模型合计从早期的 21.6 MiB 降到 17.6 MiB，是因为修掉了「PDF 把图片字节算进模型体积」的重复计入。）

| 格式 | 总数 | 成功 | 真失败 | 按设计拒绝 | 成功率 |
|---|---:|---:|---:|---:|---:|
| docx | 103 | 103 | 0 | 0 | 100% |
| pdf | 9 | 8 | 0 | 1（加密） | 100% |
| xlsx | 6 | 6 | 0 | 0 | 100% |
| pptx | 4 | 4 | 0 | 0 | 100% |
| html | 1 | 1 | 0 | 0 | 100% |
| ole2-doc / ole2-xls / ole2-ppt | 16 | 0 | 0 | 16 | n/a |

### 关于「按设计的拒绝」

成功率的分母是**我们声称支持的格式**，已排除：

- **旧版二进制** `.doc/.xls/.ppt`（16 个）：本项目的定位是**识别并提示**「请先另存为 docx」，
  而不是静默失败。这是功能，不是缺陷。
- **加密文件**（1 个 PDF）：明确报 `ENCRYPTED`，不尝试解读乱码。

早期版本的 `validate.mjs` 把它们算作失败，于是报告显示 **88.2%** ——
而真实情况是能支持的文件 **100% 都能打开**。被自己的正确行为抹黑的数字比没有数字更糟，
所以这里特意分开统计。

### 降级清单（这才是值得逐条看的部分）

55 个文件「打开成功但有内容降级」。这些都是**具体、可判断**的，例如：

- `文本框（w:txbxContent）内容已按文档顺序展开为普通段落，浮动位置未保留`
- `已解析 N 个页眉/页脚部件，文字放在 meta.custom（页眉页脚版式未在正文流中还原）`
- `文档含分节符（段落级 sectPr），页面设置取最后一节的几何参数`
- `Type0 字体 SimSun 缺少 /ToUnicode，字符已按 CID 按 gb18030 近似解码（可能有个别字不准）`
- `页面使用了裁剪路径（W/W*），裁剪区域未参与还原`
- `幻灯片背景是渐变/图片/图案填充，已忽略（无法还原）`

**为什么这件事重要**：一个「打开了但悄悄少了一半内容」的阅读器，比一个明确报错的阅读器更危险。
所以本项目要求读取器把每一处降级都写进 `stats.warnings`，并由验证脚本与 UI 显式呈现。

> 顺带修掉的一个自身的坑：`engine` 一度把「容器有 N 个条目」这种**信息性**消息也写进
> `warnings`，导致 119 个文件里 103 个被标成「有降级」—— 真正的降级因此完全看不见。
> `warnings` 的语义必须是「用户需要知道的降级」，不能当诊断日志用。

## 五、已知的内存效率问题与限制（不掩饰）

1. **每段落的对象开销偏重。** 合成 docx（20,000 段）模型 17.7 MiB，约合每段 930 字节。
   成因是 `Paragraph` + 若干 `Run` + `RunStyle` 的对象头开销累积。
   `RunStyle` 已按签名共享实例，但 `Paragraph`/`Run` 本身仍是独立对象。
   若要显著改善，需要改成扁平/列式表示 —— 那是一次较大的重构，当前未做。
2. **纯文本类的模型体积大于源文件**（3 倍量级）。同样源于「一行一个段落对象」的表示方式。
3. **惰性网格取窗口的代价与「距表头距离」同阶**：第 60,000 行附近取 14 行窗口实测 130–260 ms，
   因为压缩流无法随机定位，必须从表头扫过来。缓解方向是「记住上次扫到的位置」以便顺序续扫，
   尚未实现。
4. **`stats.imageBytes` 的语义仍未在读取器之间统一**（docx 报已驻留字节，pptx 报文档中图片总大小）。
   已用 `stats.modelBytes` 的框架统一计算缓解了影响：图片字节**永远不计入**模型体积
   （`estimateBytesSkippingBinary` 会跳过 `Uint8Array`/`ArrayBuffer`），因此两个字段不会互相污染。
   但「已占用多少图片内存」仍无法从 `imageBytes` 单独判断，需要在字段层面进一步拆分。
5. **`modelBytes` 现在由框架统一计算，不再采信读取器自报值。** 实测两个读取器朝相反方向错：
   CSV 少报 2074 倍（只估正文结构、漏掉表格数据）、PDF 多报 300 倍（把 38.9 MiB 图片算进模型）。
   框架现在用 `estimateDocumentBytes()` 统一算，并在与自报值差 5 倍以上时写一条 warning 提示作者修正。
   因此**读取器不应再往 `stats.modelBytes` 里累加任何东西**。
6. **ODF 的重复空白行有个物化硬上限（4096 行）**：超过时 `rowCount` 会被截到该值并记
   `stats.truncated`。因此「声明的行数」与「模型的 rowCount」对这类极端文件可能不一致
   （scrollbar 会显得比实际短）。真实文档几乎不触发。
7. **PDF 的保真度仍是所有格式里最低的**：它提取文本与基础图形并给出近似版面，
   不做像素级渲染。渐变、透明度混合、图案填充、CFF/Type1 的字形级还原都明确不支持，
   降级情况会写进 `stats.warnings`。测试虽然 54/54 全绿，但那些测的是**我们承诺的范围**，
   不代表能像 PDF 阅读器那样逐像素还原。
11. **位图 / 数学字体（Type3，如 TeX 的 `CMBX12`）的文字提取不出来。** 这类字体既无
    `/ToUnicode` 也无 `/Encoding`，只能按 Latin-1 直译，结果是一串无意义的码位
    （在浏览器里渲染为空白，不会显示成乱码，但复制与检索拿不到内容）。
    实测：`The RISC-V Instruction Set Manual` 这类英文数学手册受影响；中文文档不受影响。
    真正的修法需要解析 Type3 字形定义并做位图识别 —— 不在本轮范围内。
12. **超大画布的页面（如 2058×2362 的海报式 PDF）坐标仍会溢出。**
    实测 `总人数：17人.pdf` 的文本项 x 达到 6282、y 达到 12984（页面只有 2058×2362）。
    这类文件通常叠加了多层 `cm` 变换或超大 `Tm`，当前的 CTM 复合仍有偏差。
    **这不影响文本内容本身**（文字能正确提取），只影响版面位置。属已知未修项。
13. **水印类 PDF 会有负坐标**（如 `AHL-CH573.pdf` 的 x 从 −497 起）。这通常是页面外的
    水印/出血元素，属正常现象，不是 bug —— 判断坐标是否异常要排除这类。
14. **PDF 图片的显示能力（实测 33 个 PDF、530 张图）**：
    - `DCTDecode`（JPEG）→ 直接显示：**96 张**
    - 裸像素（无过滤 / FlateDecode）→ 包成 BMP 后显示：**429 张**
    - CCITT 传真 / JBIG2 位流 / 非 8 位或 CMYK 裸像素 → **5 张显示占位**并写 warning

    即 **525/530（99%）可显示**。BMP 是未压缩的，所以图片字节会比原始采样略大
    （灰度会被展成三通道）；超 `limits.maxImageBytes` 时后面的图会丢字节变占位。
    这是「能看见」与「省内存」之间的显式取舍。
8. **内存/性能断言不能放在测试套件里。** 本项目只能用单进程跑测试，
   前一个文件留下的垃圾会污染后一个文件里的堆断言（实测一条 PDF 压力测试单独跑过、全量跑失败）。
   现在 `tools/test.mjs` 在文件之间调用 `globalThis.gc()` 缓解，但**性能断言应放在 `bench/`**
   （独立进程、先写盘再读盘，能隔离测量）。
9. **惰性表的 `stats.cellCount` 是「维度上界估算」而非逐格精确值。** 物化路径下是精确计数；
   走惰性路径时由 `<dimension>` 的 `行数 × 列数` 得出，并写一条 warning 说明。
   原因：表体从未被物化，逐格计数等于把表读一遍 —— 那正是要避免的事。
   所以这个字段适合用来显示「这张表有多大」，不适合用来做精确统计。
10. **惰性网格取窗口的代价 ∝ 窗口距表头的距离**（压缩流不可随机访问）。
    已用「扫描游标」缓解：顺序向下滚动可续扫（O(窗口)），往回滚才重开流。
    实测 5 万行表：首次远跳 529 ms、表头窗口 5.6 ms、顺序续扫 5.9 ms。
    这条性质有断言钉住（`headAgain < farFirst/4`、`farAgain > seq*5`），破坏了会立刻失败。

把这些写进文档不是为了自谦，而是因为**一个不知道边界的工具没法被信任**。
