# 为什么做 LiteOffice：与 WPS 痛点的逐条对照

本文把用户提出的三个痛点拆成**可验证的设计差异**，而不是营销话术。
每条都给出「LiteOffice 怎么做」以及**「目前做到哪一步」**——后者同样重要。

> **范围坦白**：本轮交付是**可运行内核 + 只读渲染**。
> WPS 的核心价值是**编辑**，这一块 LiteOffice 尚未实现（见 [ROADMAP](ROADMAP.md)）。
> 所以下文所有「省内存」「打开快」的对比，都是**在只读浏览这个场景下**成立的。
> 把它当成「编辑器的替代品」目前是不成立的。

---

## 痛点一：无用功能多

### WPS 的处境

这不是 WPS 团队不懂产品，而是**商业模式决定的**：
免费 + 会员制的路径依赖，使得界面必须承载会员入口、模板商城、云文档推广、
PDF 转换、图片处理、思维导图、表单、日程……这些不是「功能」，是**转化漏斗**。
结果是打开一个文本文件要加载一整套内容生态。

### LiteOffice 的设计回应

**① 功能即模块，不用就不装。**
格式支持不是靠裁剪功能列表，而是**按包导入**：

```
不 import format-pdf  →  产物里没有 PDF 解析器，不占体积、不占内存
不 import render-dom  →  纯内核可用于服务端批量转换
```

`coveredFormats()` 与 `unreadableFormats()` 让 UI 能如实告诉用户
「这个格式的读取器没安装」，而不是假装支持然后失败。

**② 没有账号、云、商城、模板的代码路径。**
这是架构层面的：`core` 只有模型、格式表、上限、内存记账。
零依赖意味着**连一个网络请求库都没有** —— 这个程序在能力上就无法上传你的文件。

**③ UI 做减法。**

界面只有：标签栏、大纲/文档信息侧栏、视图区、状态栏。
没有首页推荐流、没有登录弹窗、没有会员角标。

**目前的不足**：`apps/web` 的 UI 是刻意最小的，也因此**缺少很多日常必需的易用性**
（如打印、导出为 PDF、格式刷、查找替换、多窗口）。这些不比 WPS 的「无用功能」更可省。

## 痛点二：内存占用大

这是最容易量化的一条，也最容易说空话。所以这里先讲**机制**，再讲**怎么测**。

### WPS 的处境

典型现象：打开一个大 Excel 后内存涨到数百 MB 甚至 GB，关闭文档后内存不回落。
成因通常是三件事：
1. 容器整体解压并驻留（ZIP 里的所有部件一次性读进内存）
2. 解析结果物化成完整对象树（DOM 或等价结构）
3. 大表整表物化，虚拟滚动只虚拟了「绘制」而没有虚拟「数据」

### LiteOffice 的三个机制

| 机制 | 落点 | 效果 |
|---|---|---|
| 容器只索引不解压 | `ZipReader.open()` 只扫中央目录；`streamText()` 逐块解压 | 峰值与**单个部件**同阶，而非整个文档 |
| 事件流解析 + 跳子树 | `XmlPullParser` + `skipElement()` | 不建节点树；跳过时不分配事件对象 |
| 惰性网格 | `LazyGrid.readRows()` 重新流式扫描源 XML | 峰值与**可视窗口**同阶，与全表行数无关 |
| 样式共享表 | `Cell.s` 是索引，不是对象引用 | 百万单元格不发生百万次样式对象分配 |
| DOM 虚拟化 | `render-dom` 只为可视窗口建节点 | DOM 节点数不随文档长度增长 |
| 显式释放 | `doc.dispose()` + 标签页关闭时调用 | 关闭文档后内存可回落 |

### 怎么验证（不接受「我觉得」）

```powershell
node --expose-gc bench/bench.mjs
```

输出 `bench/out/BENCHMARKS.md`，含三张表：

1. **单文档代价** —— 每个文件的「源文件 / 模型估算 / 模型÷源 / 堆增量 / 堆÷源 / 耗时」
2. **泄漏检查** —— 同一文档反复打开 15 次，线性回归斜率（B/次）。
   斜率 > 64 KiB/次 判为可疑累积泄漏 —— 这正是「关掉文档内存不回落」的量化形式
3. **虚拟化代价** —— 大表的堆增量与 `LazyGrid.cachedRows`

**已跑出的数字、以及读这些数字时必须知道的限制，都记在 [MEASUREMENTS.md](MEASUREMENTS.md)。**
其中最值得看的两条：

- 一个 50,000 行 × 20 列（**100 万单元格**）的工作簿，源 6.6 MiB，**模型只有 1.8 KiB** ——
  表体从未被物化，而任意窗口都能读到正确数据
- 泄漏检查斜率 **7,595 B/次**（阈值 64 KiB/次），末次残留低于首次 —— 未检出累积泄漏

**测量方法学上的自我约束**（写在这里以免数字被误读）：
- 堆数字受 GC 时机影响，每项测量前都尝试 `forceGc`；未加 `--expose-gc` 时输出会明确标注「数字偏噪声」
- 峰值用 5ms 轮询采样，因此是**下界**而非真实峰值
- 模型字节是 UDM 结构的**深估算**（字符串按 2 字节/字符保守估计），不是精确的 V8 占用
- **堆增量不包含源文件缓冲**（文件在取基线之前读入），对零拷贝实现需补上源文件大小
- **我们不在基准里伪造 WPS 的实测数字。** 本机没有可复现的 WPS 测量环境，
  所以对比只以「设计差异」的形式陈述，不给假的对照数据

## 痛点三：不支持多种文件格式

### WPS 的处境

WPS 对 **Microsoft 格式**支持很好（商业模式要求如此），但对开源/标准化格式的覆盖有限：
ODF 系列（`.odt/.ods/.odp`）支持残缺，`.fodt/.fods/.fodp`（扁平 ODF）基本打不开，
Markdown/CSV/JSON/RTF/EPUB 这类「非办公文档但天天遇到」的格式干脆不管。
用户于是被迫装一堆小工具。

### LiteOffice 的设计回应

**格式是一等公民，写在一张数据表里**（`packages/core/src/formats.ts`）。
新增一种格式 = 表里加一行 + 写一个读取器，UI、嗅探、文件对话框、统计、格式徽标**全部自动跟上**。

当前覆盖：

| 家族 | 格式 |
|---|---|
| OOXML | `docx` `docm` `dotx` `xlsx` `xlsm` `xltx` `pptx` `pptm` `potx` |
| ODF | `odt` `ott` `ods` `ots` `odp` `otp` `odg` **`fodt` `fods` `fodp`**（扁平 ODF，WPS 打不开） |
| 固定版式 | `pdf` |
| 纯文本/表格 | `md` `txt` `log` `csv` `tsv` `json` |
| 标记/矢量 | `html` `xml` `svg` `rtf` `epub` |
| 旧版二进制 | `doc` `xls` `ppt`（**识别并给出人话提示**，见下） |

完整矩阵与实现状态见 [FORMATS.md](FORMATS.md)。

**三个刻意的设计决定：**

**① 嗅探以内容为准，不信扩展名。**
判定顺序：魔数 → ZIP 内部结构 → 文本启发式 → 扩展名兜底。
用户会把 `.docx` 改名成 `.zip`、把 CSV 存成 `.txt`、把 ODF 存成 `.docx`。
只看扩展名会派发错读取器并报出莫名其妙的错误。

**② 旧格式要「认得出」而不是「打不开」。**
`.doc/.xls/.ppt` 是 OLE2 复合文档，不是 ZIP 结构。LiteOffice 识别出它，
然后明确告诉你「这是 Office 97-2003 二进制格式，建议另存为 docx 后再打开」，
而不是丢一个「不支持的文件类型」。**说清楚为什么，比沉默地失败有用。**

**③ 降级要显式。**
超限被截断的内容会出现在 `stats.truncated`，读取时跳过的特性出现在 `stats.warnings`，
UI 必须把它们显眼地展示。**静默丢内容比打不开更糟** —— 用户会以为文件本身有问题。

## 还没做到、且不该被含糊带过的

诚实清单：

1. **不能编辑。** 本轮是只读。这是与 WPS 最大的差距，也是路线的下一站。
2. **排版是近似的，不是像素级还原。** docx 的行距/分页/首字下沉、pptx 的复杂继承链、
   PDF 的嵌入字体字形，都做了不同程度的简化。查看「内容与结构」可靠，查看「精确版面」不可靠。
3. **PDF 不做像素级渲染。** 提取文本与基础图形并给出近似版面；CFF/Type1 字体的
   glyph 级还原、透明度混合、渐变、图案填充明确不支持。
4. **不能导出。** 没有「另存为」。
5. **桌面壳还没构建。** 设计见 [DESKTOP.md](DESKTOP.md)，`apps/desktop` 目前是方案而非可运行的壳。
6. **字体依赖系统。** Web 壳受浏览器沙箱限制，无法嵌入文档自带字体，
   因此字体替换会带来版面差异。
7. **性能尚示未在大文件上充分验证。** 基准脚本已备好，但需要真实的大文件才能给出有意义的数字。

把这些写进文档不是为了自谦，而是因为**一个不知道边界的工具没法被信任**。
