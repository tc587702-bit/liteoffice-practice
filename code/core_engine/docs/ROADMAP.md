## 第二轮：让它真的有用（编辑）

只读查看器只能解决「确认文件里是什么」。要替代 WPS 必须能改。

### 2.1 文字处理可编辑（优先级最高）
- [ ] 带撤销栈的编辑模型（区间操作 + 逆操作，而不是整篇快照 —— 后者内存爆）
- [ ] `contenteditable` 或自绘光标两种路线的**技术选型与原型对比**
- [ ] 行内格式切换、段落样式、列表
- [ ] 表格编辑
- [ ] **回写 docx**：复用 `ZipWriter`，只重写 `word/document.xml` 等被改动的部件，
      其余部件**原样搬运**（这是保真度的关键 —— 不要重新生成整个包）

**验收标准**：打开一个真实 docx → 改一段文字并加粗 → 保存 → 用 Word/WPS/LibreOffice 打开确认内容与格式正确，且未改动的部分（图片、页眉、样式）完好。往返 10 次不产生累积差异。

### 2.2 表格可编辑
- [ ] 单元格编辑、公式求值（先做常用 40 个函数）
- [ ] 回写 xlsx（同上，只重写改动的工作表部件）
- [ ] 重算并写回 `xl/calcChain.xml` 的取舍（可以删掉并标记需重算）

**验收标准**：改单元格 + 写公式 → 保存 → Excel 打开公式可重算。

### 2.3 演示可编辑
- [ ] 文本框编辑、形状拖动/缩放
- [ ] 回写 pptx

### 2.4 导出
- [ ] 导出 PDF（这条最难，需要自研排版引擎；至少先支持文字类）
- [ ] 导出 Markdown / HTML / CSV（这些简单且实用）
- [ ] 「另存为」到其它格式（docx ↔ odt 这类跨家族转换）

## 第四轮：性能与规模的纵深

- [ ] **Worker 化**：把解析放到 Web Worker，主线程只做渲染。
      验收：打开 100 MB xlsx 时页面不卡（主线程无 >50ms 的长任务）
- [ ] **索引持久化**：大文档解析后把结构索引存进 IndexedDB，
      二次打开走索引。验收：二次打开一个大文件耗时降一个数量级
- [ ] xlsx 的**按需共享字符串**：目前超限会降级，改为按需再取
- [ ] PDF 的分页惰性解析（目前整篇解析完才渲染第一页）
- [ ] 大文件的**流式首屏**：解出第一页就先渲染，不等整篇解析完
- [ ] 逐格式的性能回归基准（防止某个改动让某个格式变慢）

## 第五轮：保真度提升（按真实文件驱动）

原则：**不按规范覆盖率排期，按真实文件打不开/显示错的数量排期。**

- [ ] 建立一个「真实文件回归集」（用户授权后收集，或使用公开的 ODF/OOXML 测试套件），
      每次改动后统计「能打开率 / 结构正确率」
- [ ] docx：分节（`sectPr`）、多栏排版、首字下沉、文本框、公式（OMML）
- [ ] xlsx：条件格式、数据透视表（只读展示）、图表（`xl/charts/`）
- [ ] pptx：完整继承链（slide → layout → master → theme）、SmartArt、图表、动画（只读）
- [ ] PDF：渐变、图案填充、透明度混合、CFF/Type1 字形
- [ ] ODF：`table:number-columns-repeated` 的完整语义、章节、索引/目录域

## 明确不做

写在路线图里的「不做」比「做」更能说明项目定位：

- **不做云盘 / 账号 / 协同编辑。** 零依赖的直接后果就是程序在能力上无法上传你的文件。
  协同若要加，应以「可选插件 + 自托管」形式，不进核心。
- **不做模板商城与内容生态。** 这正是被诟病的「无用功能」的来源。
- **不做移动端原生 App。** 响应式 Web 覆盖即可。
- **不追求像素级还原。** 目标是「内容与结构可靠、版面近似」。
  像素级还原是无底洞，且与低内存目标直接冲突。
- **不实现宏 / VBA。** `docm`/`xlsm`/`pptm` 只读取内容，不执行宏（安全考量）。

---

## 怎么判断这个项目在变好

三个可量化的指标，建议每次发布都跑：

1. **`node tools/test.mjs` 全绿** + `--expose-gc` 基准里**无累积泄漏**
2. **「模型 ÷ 源文件」比值**不随格式增加而恶化
3. **真实文件回归集**里「能打开」与「结构正确」的比例单调上升
